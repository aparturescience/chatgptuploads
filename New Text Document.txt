You’re right, it isn’t a coincidence, and your strings output is the strongest evidence so far.

What points at Xiaomi’s boot-protection code

The ROM’s /system/bin/init has a BootMonitor built into init itself. Stock Android’s init has none of these strings:
Started BootMonitorThread, expiring in ...
BootMonitorThread: boot didn't complete in ...
[BootMonitor] reboot into recovery
[BootMonitor] read monitor crash '...'
RebootMonitorThread
hypsys_system also contains reboot,recovery. It’s the userspace half: it logged note boot count, checked Safe, Maintenance and Trap mode, and produced your bm_rcy_5 zip.
ro.boot.monitor=true is set, yet it’s not in the kernel command line (I checked the full line), so something inside the system sets it.
This explains why init (pid 1) set sys.powerctl=reboot,recovery on its own with no rc script and no crash. A thread inside init did it.

Timing
I decoded the boot_progress_* events in both pmsg files and compared them with boot.txt:

Boot	zygote start	preload end	reboot requested
pmsg #1	33.2 s	38.4 s	about 38.4 s
pmsg #2	18.3 s	23.5 s	about 23.5 s
boot.txt	18.3 s	23.7 s	23.77 s

The reboot request always comes about 5.2 to 5.5 s after the zygote starts, even though the absolute time differs by 15 s between boots. A fixed boot deadline wouldn’t do that. The trigger follows the zygote’s progress, so it’s either a short timer started with the zygote or a “monitor crash” signal read when preload finishes. The strings alone can’t tell me which.

To find out which, I need the surrounding strings

strings -n 4 /system_root/system/bin/init | grep -n -i -B8 -A15 "BootMonitorThread"

grep -rn -B2 -A14 "hypsys_system" /system_root/system_ext/etc/init/ /system_root/system/etc/init/ 2>/dev/null

The first two should reveal the property names (the on switch and the timeout). The third shows how hypsys_system is started.
